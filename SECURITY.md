# Current security boundary

See [current architecture](docs/current-architecture.md) for the 1.25.0 recovery-only GPU operation, CPU companion ownership, typed outcomes, and independent resource recovery. The milestone notes below describe the historical progression.

# Security and hardware safety

EcoPause treats restoration as more important than activation.

Hardware-changing contributions must not be added to the read-only probe. Any future elevated helper must be isolated from the user interface, accept a narrowly validated command schema, record original values before applying changes, verify every write by reading it back, and restore exact original values after interruption or failure.

Do not include GPU UUIDs, serial numbers, user paths, or other identifying system data in diagnostic output by default.

Recovery journals use a SHA-256 fingerprint derived from a stable device identifier rather than persisting the raw identifier. The journal digest is for corruption detection only. It must never be treated as proof that a request is authorized or trustworthy.

Dry-run plan files carry a distinct `DryRunPlan` purpose. They are not recovery-pending and the state model rejects attempts to advance them to applied or restored stages.

The activation engine persists `Prepared` before invoking a controller write. Any failure after a possible write enters rollback with `CancellationToken.None`, so cancellation of the initiating operation cannot cancel the restoration attempt. An incomplete or unverified rollback remains explicitly recovery-pending.

Startup recovery never acts solely because a journal exists. Discovery is non-recursive and bounded, and restoration requires a short-lived one-use approval tied to the exact journal path and snapshot. The engine reloads and compares the complete snapshot immediately before an approved restoration; changed content fails before controller access.

The hardware-host protocol accepts only authenticated `ActivatePrepared` and `RestorePending` commands containing a host-resolved snapshot ID. Commands are HMAC-authenticated, short-lived, strictly sequenced, and one-use. They cannot specify paths, device identifiers, power values, or native functions.

Milestone 0.7 carries the protocol over a randomly named Windows named pipe created with `PipeOptions.CurrentUserOnly` on both server and client. Frames use a four-byte length prefix, reject empty or greater-than-64-KiB payloads before allocation or processing, limit JSON nesting, and apply five-second I/O and ten-second connection timeouts. The 256-bit session bootstrap is sent only through this pipe, copied into disposable session objects, and cleared from transport buffers after serialization and parsing. The demonstration refuses elevated execution and never references the NVIDIA provider.

Milestone 0.8 introduces a manifest-declared `requireAdministrator` simulation helper and a normal-user launcher that invokes it through the Windows `runas` verb. Both pipe ends query Windows for the connected peer process ID and require an exact match with the process that was launched or the parent that launched it before exchanging the session bootstrap. The elevated helper accepts no client-supplied paths, device identifiers, power values, or native function names; its recovery journal is created beneath a helper-chosen temporary directory. It references only an in-memory controller and has no project reference to the NVIDIA provider.

For the cross-integrity connection, the normal-user server keeps `PipeOptions.CurrentUserOnly`. The elevated client connects without the client-side owner comparison, which can differ between normal and elevated Windows tokens, then immediately verifies the exact server process ID. Failure closes the client before any bootstrap or command is exchanged.

Milestone 0.9 simulates state that survives an elevated helper's abrupt termination. The fake controller and integrity-checked recovery journal live beneath a canonical run-ID directory under `%ProgramData%\EcoPauseCrashRecoverySimulation`. The helper creates that directory with protected ACLs granting full control only to Administrators and SYSTEM, rejects reparse points, and never accepts a path from the launcher. Recovery requires a new UAC-approved helper, a new mutually verified pipe session, an exact fixed simulation profile, an `Applied` journal, and an observed fake limit of 400 W before restoring exactly 450 W. Successful recovery closes the journal and removes the two known simulation files without recursive deletion.

Milestone 1.0 adds a WPF desktop process with an explicit `asInvoker` manifest and a runtime safety stop if it is nevertheless started with an administrator token. The UI does not reference Core, the hardware provider, the host protocol, or transport; it starts the already-verified normal-user simulation launcher as a child process. It disables repeated starts and blocks window closure while a lifecycle is active. A green result requires twelve exact transcript facts covering mutual PID verification, helper initialization, authenticated activation and restoration, replay and tamper rejection, clean exit, exact 450 W restoration, a closed journal, a passing lifecycle, and no NVIDIA access. Exit code zero without complete evidence is displayed as incomplete, not successful.

Milestone 1.1 lets that normal-user UI start the existing read-only probe as a separate non-elevated process. The desktop assembly still has no runtime reference to Core, the NVIDIA provider, the host protocol, or transport; its probe project reference is build-order-only. Probe output and error streams are bounded, execution has a ten-second deadline, unexpected error output is rejected, and JSON uses a strict allow-list that rejects unknown or identifying fields. Device counts, text lengths, watt values, indices, and power constraints are validated before display. Failure degrades to an unavailable card and cannot affect the fake lifecycle action. No native NVIDIA setting function is introduced or loaded.

Milestone 1.2 reads Windows' aggregate time since the last keyboard or mouse input through `GetLastInputInfo` and observes session lock/unlock notifications. It does not record keys, buttons, pointer positions, window titles, process names, or an activity history. A pure policy maps those transient signals to an on-screen five-minute countdown or a `Would pause` preview. The observer has no reference to the simulation runner and the decision event never invokes a helper, requests elevation, writes state, or changes hardware. The desktop's unsafe compilation setting is required only by .NET source-generated marshalling for the fixed `user32.dll` call; there is no handwritten pointer arithmetic.

Milestone 1.3 registers one exact Windows hotkey, `Ctrl+Shift+F3`, with `MOD_NOREPEAT`. `Alt+F3` is not registered because it conflicts with NVIDIA's Game Filter shortcut on the target class of PC. Registration is scoped to the lifetime of the normal-user desktop window and is always unregistered during disposal. If another application owns the shortcut, EcoPause reports it unavailable and leaves the manual button functional. Hotkey and button enter the same reentrancy-guarded fake lifecycle method; the hotkey cannot construct a command, supply parameters, bypass transcript evidence, or trigger from the idle-policy observer.

Milestone 1.4 gives the protected fake simulation one fixed toggle profile. The elevated helper resolves the stable run directory beneath `%ProgramData%\EcoPauseCrashRecoverySimulation`, rejects reparse points, validates the complete fixed snapshot, and decides whether the one authenticated command is `ActivatePrepared` or `RestorePending`. The normal-user launcher cannot supply an operation, device, path, power value, or user-controlled run ID. A successful activation exits normally with the integrity-checked journal `Applied` and fake hardware at 400 W. A later helper accepts recoverable `Prepared`, `Applied`, or already-`Restored` stages, restores or verifies exactly 450 W, closes the journal, and deletes only the two known files and empty run directory without recursive deletion.

The launcher writes a bounded current-user receipt containing only `Paused` or `Restored` so a restarted UI can display the likely next action. That receipt is explicitly non-authoritative: malformed or missing content becomes `Unknown`, it is never sent to the helper, and changing it cannot select activation or restoration. Desktop success requires one—and only one—complete state-specific transcript together with mutual PID verification, authenticated execution, exact fake limit, journal stage, cleanup status, passing summary, and `Real NVIDIA access: NONE`.

Milestone 1.5 replaces the single toggle profile with four compile-time allow-listed profiles: `eco-250`, `eco-300`, `eco-350`, and `eco-400`. Each has a fixed target and unique fixed run ID; the 400 W ID remains compatible with milestone 1.4 recovery. The WPF process accepts only these immutable options and validates the chosen watt value against the current read-only GPU minimum, maximum, and current limit. Numeric text is never passed to the launcher. The launcher resolves the profile ID locally and passes only its fixed run ID to the helper.

Before choosing an operation, the elevated helper checks the exact four known protected directories. More than one pending directory fails initialization. Exactly one forces restoration of that profile regardless of the newly requested profile; only zero pending profiles permits activation of the requested allow-listed profile. The helper recreates and validates the complete snapshot from its own profile registry. Receipts and state-specific transcripts now bind the profile ID to its expected target watt value, and conflicting or unknown mappings fail closed.

Milestone 1.6 introduces the first real write in a separate path that is not referenced by the WPF desktop or either simulation helper. `EcoPause.Hardware.Nvidia` remains read-only; the sole NVML setter is in `EcoPause.Hardware.Nvidia.Control`, which is referenced only by the manifest-elevated live-canary helper. The normal-user launcher performs read-only preflight, refuses elevated startup, requires the exact phrase `APPLY 400 W THEN RESTORE 450 W`, starts the helper through UAC, and mutually verifies process IDs over the existing current-user-only named pipe.

The elevated helper accepts only a random validated pipe name and the expected parent process ID. It chooses `%ProgramData%\EcoPauseLiveCanary\recovery.json`, the only GPU, the fixed 400 W target, the fixed five-second hold, and either activation or recovery. It requires exactly one NVIDIA GPU, a 450 W current or recoverable 400 W limit, a 450 W default, constraints containing both fixed values, and an exact hashed device identity. The protected directory grants full control only to Administrators and SYSTEM, rejects reparse points and unknown artifacts, and is deleted non-recursively only after exact 450 W restoration and a `Restored` journal.

For a new canary, `Prepared` is flushed before the NVML setter is called. The existing activation engine reads the 450 W baseline again, applies 400 W, reads back exactly, and persists `Applied`. The helper—not the launcher—then waits five seconds and restores 450 W with an uncancellable token before sending its final pipe result. Any code-level failure after a possible write triggers either the engine rollback or a fixed emergency 450 W write/read-back. Process termination can still interrupt in-process restoration, so a later approved run recognizes both `Prepared` and `Applied` as pending and restores before allowing another canary. An independent elevated `nvidia-smi --power-limit=450` command and a reboot or driver reload remain documented operator fallbacks.

Milestone 1.7 exercises that process-termination recovery path with a dedicated launcher and elevated helper. The helper accepts only the validated pipe name and expected parent PID; it does not accept a phase argument. Absence of a journal at the exact 450 W baseline selects `CrashAfterVerifiedTarget`. A valid pending `Prepared` or `Applied` journal selects `RecoveryOnly`, regardless of the normal-user launcher's expectation. Both the 1.6 canary helper and 1.7 drill helper take the same zero-wait global named mutex before opening the control provider, preventing overlapping live EcoPause helpers.

In the interruption phase, the authenticated activation engine persists `Prepared`, applies and reads back exactly 400 W, and persists `Applied`. Only after reloading that journal and independently reading 400 W does the helper send its bounded evidence and call `Environment.Exit(91)`, deliberately skipping in-process restoration. The normal-user launcher requires the exact exit code and complete `Applied`/400 W evidence, then queries the separate read-only provider and requires the same hashed GPU identity at 400 W before requesting the second UAC consent.

The fresh helper sees the pending journal and can process only an authenticated `RestorePending` command. Success requires exact 450 W read-back, a `Restored` journal, non-recursive cleanup of the one known file and empty directory, normal helper exit, and a second independent normal-user 450 W query. Declining the second UAC prompt deliberately leaves the GPU at the lower 400 W ceiling and retains the protected journal. Re-running the same drill prioritizes recovery; the documented independent administrator rollback and reboot fallback remain available.

Milestone 1.8 reuses the qualified 1.7 launcher and elevated helper for a manual-only persistent live toggle. The helper accepts one additional fixed behavior token, `persistent-toggle`, which cannot contain an operation, watt value, GPU index, device identity, path, or duration. With no pending journal, this behavior changes only the post-activation lifecycle: after persisting `Prepared`, applying and reading back exactly 400 W, and persisting `Applied`, the helper exits normally while retaining the protected journal. Complete pause evidence requires exit code zero, exact 400 W, `Applied`, and artifacts retained.

Any recoverable journal selects `RecoveryOnly` before behavior is considered, so neither the toggle launcher nor a changed behavior token can apply another target over pending recovery. Restoration uses the existing authenticated `RestorePending` path, exact 450 W read-back, `Restored` journal, and non-recursive cleanup. The normal-user console launcher requires an exact typed phrase, one UAC approval per invocation, strict bounded evidence, and an independent read-only final limit check. At milestone 1.8, desktop, hotkey, and idle actions remained fake-only.

Milestone 1.9 gives the normal-user WPF desktop one separate amber manual live action. The desktop retains no runtime reference to Core, the NVIDIA providers, host protocol, transport, or control assembly; its live-launcher project reference is build-order-only. A pure policy enables the button only for one sanitized NVIDIA device at exactly 450 W or 400 W, with a 450 W default and driver constraints containing both fixed values. The user must accept a state-specific warning dialog before the desktop starts the bounded normal-user launcher with a fixed desktop-confirmed mode. This mode cannot carry device, path, wattage, duration, or operation data, and UAC consent remains mandatory.

Milestone 1.10 replaces the desktop live action's single lower target with six compile-time profiles: `live-150`, `live-200`, `live-250`, `live-300`, `live-350`, and `live-400`. The WPF process can pass only one profile ID. Both the normal-user launcher and elevated helper independently resolve that ID to the same fixed wattage allow-list; arbitrary numeric text is never accepted across the elevation boundary. The desktop disables a selected profile outside the sanitized driver range and requires strict profile-specific output evidence plus a fresh read-only query.

A valid pending journal remains authoritative over the dropdown. The helper resolves the journal target to an allow-listed profile and selects `RecoveryOnly`, ignoring a different newly requested profile until exact 450 W restoration and protected cleanup complete. The canary and intentional interruption drill retain their fixed 400 W activation contract, but can recover a pending journal created by any 1.10 desktop profile. At milestone 1.10, hotkey and idle paths remained fake-only.

Desktop success requires one positive Windows-verified helper PID, normal helper exit, the exact fixed plan, authenticated execution, exactly one complete `Paused` or `Restored` transcript, independent final read-back, and correct journal retention or cleanup. The UI then performs another independent read-only probe and updates availability from observed hardware state. Output and error streams are bounded. While any lifecycle runs, live/fake buttons, target selection, refresh, hotkey re-entry, and window closure are guarded.

Milestone 1.11 routes `Ctrl+Shift+F3` to the same confirmed live-toggle method as the amber button. The hotkey supplies no additional elevated input and cannot bypass the target-specific warning dialog, UAC, profile allow-list, recovery-first helper selection, bounded transcript evidence, or fresh read-only verification. A pure routing policy keeps the green button on the persistent fake path and maps the idle observer to `PreviewOnly`; neither can reach the live launcher. An unavailable preflight, active probe, or active lifecycle causes a hotkey request to stop before any launcher starts.

Milestone 1.12 removes per-action interaction only after one startup UAC approval. The normal-user WPF process starts a normal-user session launcher through redirected standard handles. That launcher creates a random current-user-only named pipe, starts an elevated copy of itself through `runas`, and requires mutually verified Windows process IDs before accepting `ready`. The elevated broker is bound to that pipe and accepts only `toggle` with one compile-time profile ID or `shutdown`; it independently resolves the profile and rejects every other operation or value.

Milestone 1.13 changes only the persistent desktop-toggle target contract. The normal UI and both broker boundaries accept a canonical `percent-N` identity with `N` from the device-derived minimum through 99. The elevated one-shot helper independently reads the GPU default and constraints, resolves the percentage to a whole-watt target clamped to the driver minimum, persists that exact target and exact device default, then uses the existing authenticated recovery engine. No caller supplies a wattage, restoration value, GPU index, path, or operation. User hotkey and percentage preferences are non-privileged bounded JSON in `%LocalAppData%\EcoPause\settings.json`; malformed settings fall back to Ctrl+Shift+F3 and 89%.

For each toggle, the broker launches the already-qualified one-shot live helper by inheriting its elevated token, so no second UAC prompt is required. The one-shot helper still owns the protected journal, re-validates the only GPU and fixed profile, chooses recovery before activation, authenticates its operation over a new mutually verified pipe, and exits after bounded evidence. The normal desktop accepts success only from the updated startup-session transcript and a fresh read-only probe. Hotkey re-entry and overlapping commands remain guarded.

On orderly desktop shutdown, the normal launcher sends `shutdown`; the broker checks for an allow-listed pending limit and restores exactly 450 W through the same one-shot recovery helper before acknowledging exit. If the desktop or launcher disappears, the broker detects its verified pipe disconnect and attempts the same restoration. A hard termination can still interrupt that attempt, so the protected journal remains authoritative and the next approved startup recovers before reporting ready. The WPF UI itself remains `asInvoker`; no service, scheduled task, saved credential, UAC bypass, or permanently elevated desktop process is introduced.
